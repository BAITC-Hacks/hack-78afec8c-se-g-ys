## Согласованный пользовательский цикл

1. Участник изучает исходные показатели пяти районов и каталог 14 мероприятий.
2. Составляет черновик: видит стоимость, лаги, заявленные эффекты, остаток бюджета и ограничения. Итоговый Score и разбор до принятия не раскрываются.
3. Подтверждает допустимый сценарий кнопкой «Принять пять решений».
4. Получает итог на Q8 и AI-разбор, основанный только на данных модели.
5. Может создать редактируемую копию сценария и повторить попытку. Все попытки начинаются с исходных показателей и бюджета 100; результаты предыдущих попыток сохраняются для сравнения.

Попыток может быть неограниченное количество. Принятые сценарии не изменяются при редактировании новых черновиков.

## Фаза 1 — Minimal Viable Core

### Стек и границы компонентов

- Математическое ядро на Python: валидатор, расчёт Score, поиск точечной замены и подготовка расчётных фактов. Ядро не зависит от интерфейса или вызовов OpenAI.
- FastAPI: API приложения и серверная интеграция с OpenAI. Итоговая проверка допустимости и расчёт результата выполняются на сервере по исходным данным организаторов.
- React/TypeScript: каталог, редактирование черновика, отображение бюджета и ограничений, принятие сценария, результаты, обоснования, история и сравнение. Формула Score не дублируется на фронтенде.
- `localStorage`: история принятых попыток в браузере, без аккаунтов и серверной базы истории в первой фазе.

Проверка черновика не раскрывает Score, итоговые показатели или рекомендацию замены. Неполный черновик можно редактировать; требование ровно пяти решений обязательно при принятии. Принятие запускает полную серверную проверку и расчёт; AI-разбор запрашивается отдельно и не задерживает отображение числового результата.

### Валидатор и калькулятор

Проверки допустимости:

1. Все мероприятия существуют в каталоге.
2. Выбрано ровно пять решений.
3. Суммарная стоимость не превышает 100.
4. Мероприятия не повторяются.
5. Для районного мероприятия выбран ровно один существующий район.
6. Для городского мероприятия район не указан.
7. В каждом направлении не более двух мероприятий.
8. Соблюдены несовместимости: M1/M3 в любом районе; M4/M7 и M5/M13 при совпадении района.

Калькулятор применяет эффекты с учётом лагов, фиксированные синергии и ограничение показателей диапазоном 0–100, затем рассчитывает оценки районов, средневзвешенную оценку города, число критических показателей и итоговый Score по формуле организаторов. Значение ровно 40 не является критическим; порядок решений не влияет на результат. Невалидному набору не присваивается Score.

Для объяснения каждого решения в первой фазе доступны его стоимость, лаг, район действия и эффекты на показатели с учётом лага; активированные синергии указываются отдельно. Эффекты отдельных мероприятий до общего клиппинга не выдаются за независимые слагаемые итогового прироста Score. Разложение прироста Score по Шепли остаётся в третьей фазе.

### Предупреждение о недостатке бюджета

Разрешён промежуточный выбор, который сам укладывается в бюджет и ограничения, но заведомо не оставляет денег для дополнения до пяти решений. Вместо блокировки такого выбора интерфейс показывает предупреждение с предложением изменить уже выбранные мероприятия. Принятие неполного набора недоступно; фактическое превышение бюджета по-прежнему запрещено.

Контрольный пример: M3/Нура (30), M5/Сарыарка (25), M13/Алматы (28). Стоимость 83, остаток 17, а два самых дешёвых оставшихся мероприятия стоят вместе 20. Черновик сохраняется редактируемым с предупреждением.

Для первой фазы достаточно гарантированно выявляемой нехватки: если даже сумма нужного количества самых дешёвых ещё не выбранных мероприятий превышает остаток, дополнить черновик без изменений невозможно. Эта нижняя оценка не доказывает существование допустимого завершения при достаточном остатке: сочетания направлений и несовместимости могут дополнительно ограничивать выбор. Отсутствие предупреждения не заменяет окончательную проверку всех правил.

### Локальный поиск одной замены

Рассматриваются замена мероприятия, перенос района и их сочетание при неизменных остальных четырёх решениях. Каждый кандидат проходит полный валидатор и расчёт. Глобальный перебор для этого не требуется.

Для текущего каталога существует 54 варианта отдельного решения: десять районных мероприятий × пять районов и четыре городских мероприятия. На пять заменяемых позиций приходится не более 270 кандидатов до исключения неизменного сценария, повторов и недопустимых сочетаний.

Согласованный порядок выбора рекомендации:

1. Наибольший строго положительный прирост неокруглённого Score.
2. При равном приросте — меньшая стоимость итогового сценария.
3. При равенстве прироста и стоимости — фиксированный порядок идентификаторов мероприятий и районов, независимый от порядка ввода решений.

Округление применяется только для отображения и не определяет равенство кандидатов. Меньшая стоимость не добавляет баллы и используется только для выбора между сценариями с одинаковым Score. Если улучшения одной заменой нет, система сообщает об этом без утверждения о достижении глобального максимума; нулевой прирост не выдаётся за улучшение.

### AI-аналитик

Провайдер первой фазы — OpenAI. Рекомендуемый способ интеграции — серверный вызов Responses API со Structured Outputs и строгой JSON Schema для отчёта; конкретная модель выбирается с учётом доступа команды и проверки качества. Ключ API не передаётся в браузер и не хранится в истории попыток.

Структурированный отчёт состоит из четырёх блоков:

1. Executive Summary.
2. Победы.
3. Оставшиеся проблемы и компромиссы.
4. Точечная замена.

Числа и допустимость рекомендаций определяются кодом. AI объясняет предоставленные результаты без прогнозов аварий, вероятностей событий и других утверждений, не подкреплённых моделью. Каждый содержательный вывод сопровождается раскрываемым обоснованием из расчётных фактов.

Для AI-разбора сервер формирует факты по проверенным решениям и данным организаторов. Присланные браузером числовые результаты или содержимое локальной истории не заменяют серверный расчёт.

В [официальном руководстве OpenAI по Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) подтверждена поддержка JSON Schema в Responses API через `text.format`. Руководство отдельно отмечает возможность содержательных ошибок, отказов и неполных ответов: соответствие схеме не заменяет проверку фактов.

### Проверяемые обоснования AI-разбора

Приложение подготавливает факты из исходных данных, результата сценария и локального поиска и присваивает им идентификаторы. AI получает эти факты и возвращает пояснения со ссылками на их идентификаторы. Числовые значения в раскрываемых обоснованиях подставляет приложение из расчёта.

Для каждого вывода проверяются наличие обоснования и принадлежность всех ссылок к фактам текущего сценария или рассчитанной для него альтернативы. Неизвестные ссылки и отсутствие обязательных обоснований делают ответ некорректным и включают согласованный базовый разбор. Предлагаемая точечная замена должна совпадать с результатом локального поиска.

Проверка структуры и существования ссылок не доказывает правильность свободного текста. При реализации необходимо отдельно проверить, что объяснения соответствуют приведённым фактам, не приписывают неподтверждённую причинность и не вводят выдуманные значения; обещание нулевого риска галлюцинаций не является свойством этого формата.

### Поведение при сбое AI

Принятая попытка сохраняется после успешной проверки и расчёта независимо от доступности AI. Score, изменения показателей и рассчитанная точечная замена отображаются без ожидания AI-разбора.

При ошибке, тайм-ауте или некорректном ответе AI пользователь получает краткое шаблонное объяснение с явной отметкой «Базовый разбор» и кнопку «Повторить AI-разбор». Повторный запрос относится к той же попытке: обновляет только объяснение, не создаёт новую запись истории и не меняет решения или числовой результат.

Рабочая интеграция с LLM обязательна для первой фазы. Базовый разбор обеспечивает устойчивость при сбоях, но не заменяет реализацию AI-анализа.

### Базовый интерфейс

Таблица или сетка пяти районов, каталог мероприятий, счётчик бюджета и выбранных решений, принятие сценария, результат и AI-разбор, история и сравнение попыток. Интерактивная карта не является зависимостью первого рабочего цикла.

### Русский и казахский языки

Первая фаза поддерживает русский (`ru`) и казахский (`kk`); при первом запуске выбран русский. Переводятся элементы интерфейса, описания районов и мероприятий, названия показателей, сообщения валидатора, предупреждения, базовый разбор и AI-разбор. Названия QALA и Astana Quality of Life Score сохраняются как имена продукта и итоговой оценки.

Статические тексты и терминология хранятся в согласованных словарях переводов. Для четырёх блоков AI-разбора используются локализованные заголовки; английское рабочее название Executive Summary не означает обязательного английского текста в интерфейсе.

Язык влияет только на представление: идентификаторы мероприятий и районов, решения, числовые результаты и ссылки на расчётные факты остаются одинаковыми. Переключение языка не сбрасывает черновик, не создаёт новую попытку и не меняет Score.

После принятия сценария AI-разбор автоматически запрашивается на текущем языке. При первом переключении на второй язык автоматически запрашивается отдельная языковая версия по тем же расчётным фактам. Успешно проверенные версии сохраняются раздельно для `ru` и `kk` в той же записи попытки; последующие переключения используют сохранённый результат без нового запроса к OpenAI.

Пока новая версия загружается, доступны рассчитанные числа и базовый разбор на выбранном языке. При ошибке действует тот же режим базового разбора с явным повторным запросом. Быстрое переключение языков не должно создавать параллельные дубликаты запроса для одной попытки и одного языка; ответ сохраняется для своего языка независимо от того, какой язык открыт к моменту его получения.

### Хранение истории

В первой фазе история хранится в `localStorage` текущего браузера: это сохраняет принятые попытки между посещениями, в отличие от `sessionStorage`, ограниченного сеансом вкладки. Регистрация, аккаунты и синхронизация между устройствами не входят в первую фазу.

История включает принятые решения, их числовые результаты и полученные языковые версии AI-разбора, включая первую попытку, для последующего сравнения. Очистка данных сайта удаляет локальную историю; локальное сохранение не означает резервное копирование или гарантированно неограниченную ёмкость хранилища.

### Локальный запуск и защита

Основной путь запуска после установки необходимых инструментов и настройки окружения — `bash run.sh`. Скрипт должен запускать сборку и сервисы через Docker Compose; прямой запуск через Compose также документируется. Конкретные файлы запуска ещё предстоит реализовать.

README должен явно отделять первоначальную подготовку окружения от последующего запуска одной командой. Конфигурация задаётся через документированный файл окружения с безопасным `.env.example`; `OPENAI_API_KEY` доступен только серверу, а файл с настоящим ключом исключается из Git. Конкретная модель и остальные параметры интеграции описываются после выбора и реализации.

Готовность запуска проверяется из чистой копии репозитория по инструкции README. Перед защитой образы собираются заранее и проверяется полный сценарий на ноутбуке команды. Локальная математика и базовый разбор работают без OpenAI; для живого AI-разбора требуется доступ к OpenAI API по сети.

### Условия готовности первой фазы

Полный пользовательский цикл проходит от выбора до повторной попытки и сравнения на русском и казахском языках. Проверены формула, граничное значение 40, синергии, несовместимости, независимость от порядка решений и допустимость предлагаемых замен; смена языка сохраняет решения и числовые результаты. Проверены локализованные предупреждения, базовый разбор и живой AI-разбор на обоих языках. README содержит архитектуру, реальные скриншоты, описание переменных окружения и проверенные инструкции; из чистой копии репозитория воспроизводятся запуск и контрольный сценарий. Подготовка документации входит в первую фазу.

### Порядок реализации первой фазы

1. Подготовить структуру Python/FastAPI и React/TypeScript, версионированные данные организаторов, каркас Docker Compose и README с фактическим состоянием проекта.
2. Реализовать математическое ядро и автоматизированные проверки официального примера, всех правил, порога 40, синергий, клиппинга и независимости результата от порядка решений. Равенство Score определять без округления для отображения и без случайных погрешностей двоичной арифметики.
3. Соединить API и минимальный интерфейс в первый рабочий цикл: каталог, черновик с контролем бюджета, принятие пяти решений и результат. Сразу отделить статические тексты от компонентов и подготовить русский и казахский словари.
4. Добавить локальный поиск с согласованным порядком выбора, расчётные факты, базовый разбор, историю и сравнение повторных попыток.
5. Подключить OpenAI: четыре блока отчёта, проверяемые обоснования, обработку ошибок, повторный запрос и сохранение двух языковых версий. Проверить живые ответы на русском и казахском.
6. Проверить полный цикл, сохранение истории после перезапуска, переключение языков, бюджетное предупреждение и поведение при сбое AI. Проверить, что неполный набор не получает итоговый Score, а локальная рекомендация всегда допустима.
7. Завершить запуск через `bash run.sh`, пройти README из чистой копии, добавить скриншоты готового приложения и отрепетировать локальную защиту.

### Технические задачи, не требующие продолжения продуктового интервью

- Выбор конкретной доступной модели OpenAI по качеству русских и казахских отчётов, задержке и стоимости. Модель задаётся серверной конфигурацией `OPENAI_MODEL`; доступ и пригодность подтверждаются при реализации, а фактическое значение документируется.
- Форматы API, структура файлов, библиотеки UI, точные тайм-ауты и тестовые инструменты выбираются при реализации в рамках согласованного стека и поведения.
- Срок сдачи и состав команды нужны для календарного распределения работы, но не меняют зафиксированный порядок приоритетов: сначала полный цикл первой фазы.

Детали глобального сравнения и Шепли остаются вопросами соответствующих дополнительных фаз и не блокируют первую. Новый продуктовый вопрос нужен, если при реализации обнаружится противоречие требованиям или потребуется изменить согласованное поведение; обычные технические решения не требуют нового раунда интервью.

## Числовые проверки при проектировании

Проверено отдельными вычислениями по данным организаторов; эти проверки пока не являются автоматизированными тестами приложения:

- Базовые оценки районов: Есиль 62.99, Алматы 57.06, Сарыарка 54.65, Байконур 56.63, Нура 49.18.
- Базовая средневзвешенная оценка: 56.8624; два критических показателя; базовый Score: 52.55768.
- Пример M7/Нура, M8/Нура, M10/Нура, M12/город, M5/Сарыарка: стоимость 95; Score 56.54307; прирост 3.98539.
- Минимальная стоимость допустимого набора: 61, мероприятия M4, M9, M10, M11, M12.
- Допустимых наборов идентификаторов мероприятий: 1181. С учётом выбора районов и территориальных несовместимостей: 694395 сценариев, без учёта порядка решений.

Число 694395 независимо совпало при прямом перечислении назначений районов и комбинаторном подсчёте. Для набора с r районными мероприятиями и p присутствующими парами районных конфликтов число допустимых назначений равно 5^(r − 2p) × 20^p; конфликтующие пары M4/M7 и M5/M13 не имеют общих мероприятий.

Прежняя оценка «371k» не подтверждается текущими правилами. Обещание вычислить глобальный максимум примерно за секунду требует отдельного измерения реализации.
